# mutation: the unit tests pin the plumbing, not the tuning; face-meme thresholds have no gate at all

## Question
M3 ("tune from data") relies on regression gates (unit tests and the HaGRID eval) to prove a threshold change is intended. How much of `memes.js` is actually protected? If a threshold or veto in a score were silently changed, would anything fail?

## Method
Mutation testing of `memes.js` on master (`lab/mutation/mutate.mjs`). Mutants: every non-0/1 numeric literal x1.25 and x0.8 (294), every ` not(` veto replaced by 1 (27), `<`/`>` flips (15), `&&`/`||` swaps (27): 363 in all, each in its own copy of the repo, run against `node --test` (memes, face-regression, crop, csp tests; the other test files do not import memes.js, and adding them changes nothing). A mutant is "killed" if the suite fails. ~50 s total, 6 workers. Second pass (`hagrid-kill.mjs`): the 35 survivors in `fingerState`/`handFeatures` re-run through `demo/eval-hagrid.js --json` on the real HaGRID test landmarks; "moves" = any recall/precision/false-trigger number changes by >= 0.005. Many x1.25/x0.8 mutants of a tuned ramp are legitimate "tolerated" changes, so the score is a measure of how much tuning is *pinned*, not of bugs. Equivalent mutants are included (e.g. `/ 2` -> `/ 2.5` on a blendshape average is a real change, but the `lm.length >= 455` and `234` index mutants only matter for malformed arrays).

## Results
Killed by the unit tests: **114 of 363 (31 %)**. By kind: numbers 78/294, vetoes 6/27, comparisons 14/15, logic 16/27. By region (killed/total):

| region | killed |
|---|---|
| face-meme score lines (pop … sleepy) | 5 / 122 |
| hand-meme score lines + stare | 2 / 37 |
| `outerUp`/`browsRaised` helpers | 3 / 18 |
| `fingerState`/`handFeatures` | 80 / 115 |
| `faceFeatures` | 15 / 45 |
| chooser (EMA .6/.4, 0.35 floor, 0.08 margin, 220/600 ms holds, GAP) | 9 / 22 |

Per meme score lines killed: pop 0/11, shocked 0/14, hiss 0/9, smile 0/10, smug 0/13, side-eye 0/9, lookaway 0/5, sleepy 0/4, think 0/6, point 0/9, laugh-point 0/8, angry-fist 0/4, stop 0/2; close-stare 1/10, crying 2/20, huh 2/17, fistbump 1/5, wizard 1/1. Only 6 of 27 deleted vetoes are noticed (the others include the ones identified in `reachability` / `hand-near-face` / `hands-up` as missing, but also vetoes that exist and nobody tests).

Chooser: nothing tests the smoothing constant (0.6/0.4), the 0.35 floor, the 0.08 switch margin, the 600 ms fall-back hold or the 220 ms hold beyond "about 0.2 s" (only the 220 ms *decrease* is killed); `GAP_MS` 1600/2500 survives. These are exactly the numbers `choose-dynamics`, `jitter-chooser` and `chooser-fuzz` characterised.

HaGRID pass over the 35 hand survivors: **17 move the gate** (e.g. `ext` 1.12 -> 1.4 collapses pointing recall by .96; thumbsUp height 0.35 -> 0.44 costs .21 thumbs-up recall; 0.55 -> 0.44 in the thumb test costs .21 shaka recall), so the M1 eval *does* pin finger-state tuning that the unit tests do not. **18 are invisible to it**: all 12 `handAtChin` lines (127–131), `handsUp` (135), `twoPalms` (136), the fist-under-chin override (137–138), and `validHand`'s length 21 (3). These need a face and a second hand, which `eval-hagrid` does not supply (`handFeatures([hand], null)`, one hand at a time).

## Reading
- The suite is a good guard on structure (comparison direction, finger logic, plumbing) and a weak one on tuning. Face expression scoring (the largest block of tuned numbers, 11 of 21 memes) is **unprotected by any gate**: any ramp edge can move 25 % with CI green. `face-blendshape-fer` found no clean open benchmark, so a data gate is unlikely soon; a *golden-table* test is cheap instead.
- Hand-with-face logic (chin, hands-up, two-palms) is protected by neither tests nor HaGRID; those are also where every `lab/` bug so far was found (think steals thumbs, yippee loses ties, wizard on duplicates).
- Caveat: the mutation score is meant as a map, not a target; 100 % is not wanted for hand-tuned ramps. The aim is that deliberate retuning shows up as an explicit golden diff.

## What the planner should do next
1. Add a **golden score table** test: a fixed list of ~40 feature vectors (each meme at its ramp's lo / mid / hi plus the typical competitors, including hand x face combos from `lab/reachability/matrix.mjs`), asserting the argmax and the rounded score (2 decimals) stored in a fixture; retuning then requires regenerating the fixture, a reviewable diff. Acceptance: re-run `lab/mutation/mutate.mjs`, face-meme region kills >= 70 % and every `not(` veto in a meme is killed.
2. Add chooser pins on numbers the owner has seen quoted ("about 0.2 s", "0.6 s"): a replay asserting the switch time window (e.g. 200–300 ms in, 650–900 ms back to stare, from `choose-dynamics`) and that a 0.34 vs 0.36 steady score straddles the floor.
3. Extend `eval-hagrid` (or a new `eval-hand-face`) with a pose-over-synthetic-face and a two-hand pair, so chin/hands-up/two-palms thresholds are gated before M3 touches them (reuse `lab/hand-near-face`, `lab/hands-up` placement code).
