# Does the shared meme show what the live view shows? (snap() crop vs `.cam` view)

Date 2026-11-19. Track (b): simulation. Not a GPU job.

## Question
`snap()` in `app.js` crops the camera frame into a 1080×675 box (aspect 1.60) with a cover fit. The live view is the
`.cam` grid row, which is half of the screen height minus the button bar. On a phone that box is nearly square (aspect
about 1.1–1.3). If the two crops differ, a pose that was in view when the meme switched can be cut off in the shared
image. Success criterion 5 (owner checks every pose on an iPhone) would not catch this, because it looks at the live view.

## Method
`lab/snap-crop/sim.mjs` computes the window of the video frame kept by each cover fit. The frame sizes are portrait
720×1280, landscape 1280×720 and 4:3 640×480. The boxes are an iPhone PWA (390×844 minus safe area and bar), iPhone Safari
(390×664 visible) and a 360×640 phone. It then scores the 229,392 HaGRID v2 test hand bboxes (normalized, from the
annotation JSONs already fetched in `.agent-work/hg`). For each bbox it records the share fully inside the window, and
the share more than half outside it. Output: `lab/snap-crop/output.txt`.

**Caveat:** HaGRID hands are not framed for a phone selfie, so the numbers are a proxy for where a hand sits in a
frame, not a measurement of real use. The window sizes are exact geometry, but the bbox shares are only indicative.
I could not check which video dimensions iOS Safari really delivers. I assume it is portrait (width < height) when
the phone is held upright, as the `1280×720` ideal in `getUserMedia` is rotated to match.

## Results
| frame | box | share of frame kept: live / snap | hand fully in: live / snap | hand >50% out: live / snap |
|---|---|---|---|---|
| portrait 720×1280 | iPhone PWA | .52 / .35 | .74 / .46 | .12 / .26 |
| portrait 720×1280 | iPhone Safari | .42 / .35 | .60 / .46 | .19 / .26 |
| portrait 720×1280 | 360×640 | .44 / .35 | .62 / .46 | .17 / .26 |
| landscape 1280×720 | any | .61–.75 / .90 | .81–.93 / .99 | ≤.04 / 0 |
| 4:3 640×480 | any | .82–1.0 / .83 | .97–.99 / .94 | ~0 / .02 |

- With an upright portrait frame the meme keeps **35 %** of the frame, a full-width band across the middle third
  (exact: `450/1280` of the height). The live view shows 42–52 %. The snap drops about a quarter to a third of what
  the user saw, always from the top and bottom, so a raised hand or the top of the head can be cut.
- With a landscape frame the snap shows *more* than the live view (.90 vs .61–.75), so the user sees a tighter frame
  than the file contains. That is harmless for cutoffs but means the two never match.
- In the proxy, a hand lies fully inside the snap for 46 % of boxes with portrait video, against 60–74 % live.

## Other things noticed (not tested)
- `snap()` draws the caption with `Anton`, which comes from Google Fonts via `<link>`. Canvas does not wait for a web
  font, so the first snap can use Impact/Arial Black if the font has not loaded. Offline it never loads (see
  `2026-11-19-offline-sw.md` for why nothing is cached on the first visit). A `document.fonts.load("120px Anton")`
  before drawing would remove the race. Browser unverified.
- The caption is drawn at the top edge of the cat half with `maxWidth = W-60`, so a long caption is squeezed
  horizontally, not wrapped. Check the longest caption in `memes.js`.

## What the planner should do next
1. Make the snap crop use the live view's aspect (`cam.clientWidth / cam.clientHeight`) for the camera part, or
   choose the camera box height so a portrait frame shows at least what is on screen. Acceptance: for a 720×1280 frame
   and a 390×357 `.cam` box, the snap crops the same region as the live view, and a unit test of the extracted
   crop-window function checks it for the three frame sizes above.
2. Add a "hand at the top/bottom of the frame" case to the M2 smoke test, comparing the snap to a screenshot of `.cam`.
3. Owner check on the iPhone: take a meme with a hand raised high and see whether it is cut off. That confirms the
   portrait assumption.
